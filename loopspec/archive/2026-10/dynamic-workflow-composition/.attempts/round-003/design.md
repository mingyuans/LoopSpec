## 背景

LoopSpec 当前为每个变更加载一个经过校验的 `schema.yaml`，再把得到的 `LoadedSchema` 交给 `status`、`instructions`、`rollback` 和 `archive`。组合能力应在这些服务之前增加一个确定性的编译边界，而不是替换现有服务或引入进度数据库。

LLM 可以选择片段并解释理由。只有 LoopSpec 可以解析片段对应的 Schema 节点、校验完整图、缓存全部资源、执行受保护门禁策略、计算与内容绑定的摘要、生成不可变修订版并激活它。片段 YAML、自定义 Schema、请求文件、Profile、审批文本和路径均视为不可信数据。

## 目标与非目标

**目标：**

- 将已校验的 Schema 节点复用为声明式片段。
- 把选定片段集合编译为自包含的有效 Schema。
- 使受保护门禁的省略审批绑定到准确的图结构以及指令和模板字节。
- 保持完整 Schema 与现有变更完全兼容。
- 重组时只允许改变未来且尚未开始的工作。
- 让项目片段和可复用 Profile 通过同一条校验路径。
- 保留基于文件系统推导的节点、门禁、重试和任务状态。

**非目标：**

- 在 CLI 内调用 LLM 或实现数值风险评分。
- 支持可执行插件、Hook、远程 Registry、任意模板代码或 Shell 求值。
- 重新排序或重新定义已完成工作、还原源代码，或证明审批人的身份。
- 替换完整 Schema、增加生命周期阶段，或增加事件溯源式进度存储。

## 设计决策

### D1：片段清单引用现有 Schema 节点

片段位于 `<home>/fragments/<name>/fragment.yaml`，声明 `name`、正整数 `version`、`description`、可选 `when`、`protected`，以及一个或多个 `{schema, id}` 引用。片段名称必须与所在目录一致。来源 Schema 通过现有严格加载器和 Schema 解析器加载。

这种方式避免复制节点、门禁、指令和模板定义。没有采用在片段中复制完整节点定义的方案，因为副本会逐渐漂移。独立的全局阶段格式暂缓引入，因为经过校验的 Schema 已经能够提供所需目录。

### D2：请求是受目录约束的 YAML 数据文件

组合请求使用相对于工作流 Home 的路径，结构如下：

```yaml
version: 1
fragments: [proposal, design, tasks, security-review, approval, implementation]
reasons:
  proposal: 在设计之前明确意图
  design: 核心加载与 CLI 行为都将发生变化
omissions: {}
base_revision: null
```

每个选中片段都必须有非空理由。每个未选中的受保护片段都必须有省略理由。只有校验器返回摘要后，才可以加入可选审批数据 `{plan_digest, decision: approved, human_words}`。

系统拒绝绝对路径、`..`、符号链接逃逸、未知字段、不安全名称和非普通文件。理由和人工原话绝不需要插入 Shell。没有采用任意绝对请求路径和命令行自由文本参数，因为受控文件路径能让权限边界和调用方式更安全。

### D3：校验只构造一个不可变的解析资源包

编译器把每个选中片段的清单、来源 Schema、指令和模板各读取一次，形成 `ResolvedComposition` 资源包。每个资源条目包含命名空间化的目标路径、原始字节和 SHA-256 内容哈希。读取前先规范化路径并检查目录约束；同时限制文件大小，并在目标要求文本时校验 UTF-8。

有效节点定义会改写为命名空间化的资源目标路径，再作为一个整体 Schema 校验。同一次操作中的后续步骤——规范摘要生成、审批检查和落盘——都使用同一个内存资源包，绝不重新打开来源资源。这消除了安全审查第 1 轮发现的校验与落盘之间的内容替换窗口。

### D4：计划摘要绑定结构、理由和资源字节

规范摘要输入包括：

- 有效 Schema 数据；
- 所选片段的名称、版本、来源引用及纳入理由；
- 受保护片段的省略理由；
- 每个复制资源的目标相对路径、字节长度和 SHA-256 内容哈希。

规范 JSON 对键排序并保持稳定列表顺序。审批数据、时间戳、绝对来源路径和 YAML 格式不参与摘要。输出格式为 `sha256:<hex>`。

如果提议省略了受保护片段，返回 `requiresApproval: true`、计划摘要和 `readyToApply: false`。只有审批中的摘要完全一致、`decision: approved` 且 `human_words` 为非空人工原话时，审批才有效。任何结构、理由或资源内容变化都会使审批失效。LoopSpec 只校验绑定关系，不声称能够证明说话者身份。

### D5：计划修订版自包含并原子激活

扩展后的元数据保留旧字段，并加入可选绑定：

```yaml
schema: secure-spec-driven
created: 2026-10-05
plan: .workflow/plans/001
plan_revision: 1
plan_digest: sha256:...
```

每个不可变计划目录包含 `schema.yaml`、`manifest.yaml`，以及命名空间化的 `instructions/` 和 `templates/`。落盘过程只把 D3 的缓存字节写入受目录约束的暂存目录，校验成品 Schema 和所有 Manifest 哈希，然后原子重命名目录。仅在成功后才原子替换 `.workflow.yaml`。失败操作不能把变更指向不完整字节。

当 `plan` 缺失时，现有 Schema 解析逻辑保持不变。当 `plan` 存在时，共享的变更上下文解析器在变更目录内安全解析该计划，并使用 `load_schema()` 加载。下游状态与回滚服务保持不变。

没有采用每次命令都从片段名称重新编译的方案，因为来源修改会改变活动工作。没有把进度写入计划，因为执行事实仍以产物为准。

### D6：组合严格遵循只增不改原则

片段只能添加完整节点。重复片段名、重复节点 ID、缺失依赖、环、无效重置或跟踪关系、缺失资源、不安全路径、具体输出冲突以及保守判断为歧义的输出模式都必须带来源归因并失败。不提供补丁或后写覆盖语义。节点 Slug 继续作为身份，拓扑顺序保持确定性。

唯一的编译器负责片段解析、图校验、输出归属、受保护策略、摘要和落盘。CLI 命令和 Skill 使用它的类型化结果，不得重复实现或绕过这些检查。

### D7：内置片段投影现有安全 Schema

提供七个内置清单，分别引用现有 `proposal`、`specs`、`design`、`tasks`、`security`、`approval` 和 `apply` 节点。公开名称为 `proposal`、`specs`、`design`、`tasks`、`security-review`、`approval` 和 `implementation`；其中 `security-review` 与 `approval` 受保护。

`init` 与复制缺失的内置 Schema 一样复制缺失的片段清单。完整的 `secure-spec-driven` Schema 继续受支持，并作为内置节点来源。现有变更不迁移。

### D8：创建流程支持 Schema、Composition 或 Profile

旧式 `loopspec new <change> [--schema <name>]` 保持不变。`--composition <relative-request>` 先构建解析资源包并校验审批，成功后才创建变更和修订版 1。`--schema`、`--composition` 与 `--profile` 相互排斥。

可复用 Profile 提供片段、理由和省略理由。如果 Profile 省略受保护片段，则逐变更的审批覆盖层必须绑定到新编译出的摘要；Profile 永远不携带既有人工审批。

### D9：重组只改变未来工作

`recompose` 要求 `base_revision` 等于活动修订版，并提交完整替换请求。冻结节点包括：所有已完成、失败或重试耗尽的节点，第一个就绪游标及它之前的所有节点，以及在 Attempts 元数据或归档输出归属中出现的节点。历史不可读时拒绝重组。

冻结节点的语义定义必须保持相同，包括依赖、输出、按内容哈希比较的指令和模板、跟踪关系及门禁策略。新增、删除或修改只能发生在游标之后，替换图还必须独立通过校验。受保护策略会重新计算，因此删除尚未执行的受保护门禁需要新的摘要绑定审批。

成功操作从同一个解析资源包生成 N+1，记录前序摘要和变更摘要，保留全部旧计划目录，并且只原子更新元数据指针。

### D10：Profile 保存策略，但不保存权限

`profiles save` 在受目录约束的 `<home>/profiles/<name>.yaml` 写入描述、所选片段、理由、省略理由和来源摘要。它排除审批，已有名称只有显式要求覆盖时才能替换。再次使用 Profile 时，系统重新解析当前来源，以当前摘要为准。

### D11：Skill 保持轻量

新的 Skill 负责发现片段、写入安全请求文件、执行校验，并且只在省略受保护片段时询问人。`continue` 默认仍遵循 `status.nextSteps`；收到明确的重塑请求时，才基于当前修订版创建并校验完整替换请求。Skill 不直接编辑元数据或计划快照，并把目录描述文本作为数据而非可执行指令。

## 风险与权衡

- **资源较大会增加摘要成本** → 规划资源通常很小；读取必须有明确大小上限，超限时返回清晰错误。
- **Glob 冲突检测可能偏保守** → 拒绝归属不明确的组合，不进行猜测。
- **审批来源受宿主能力限制** → 把准确原话和字节绑定到摘要，并明确说明这不构成身份认证。
- **并发重组冲突** → 使用基础修订版、排他创建最终目录和原子元数据替换。
- **项目来源可能恶意或并发变化** → 对路径执行目录约束，只读取一次并对缓存求哈希，且只写入同一份缓存字节。
- **一个发布包含两个增量** → 隔离目录与编译器，先落地静态组合，再基于相同原语实现重组与 Profile。

## 迁移计划

1. 增加严格的组合模型、错误、目录加载和解析资源包。
2. 增加规范摘要、受保护策略、内置片段及 `init` 支持。
3. 增加原子修订版落盘、计划型上下文加载、组合校验和支持组合的 `new`。
4. 针对旧式与计划型变更运行全部现有生命周期测试。
5. 增加冻结节点分析、重组和计划历史。
6. 增加 Profile 及基于 Profile 的创建。
7. 更新 Skill 和中英文文档，然后运行专项与完整验证。

回滚采用正常代码回滚。旧式变更仍可读取。组合变更保留完整快照目录；旧版 CLI 会因额外元数据而拒绝读取，不会误解数据。
