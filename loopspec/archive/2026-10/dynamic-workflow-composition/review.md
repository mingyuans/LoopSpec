# 新版方案评审摘要

## 要解决的问题

固定的大需求模板对前端小需求和局部 Bugfix 过重；QA 返工又可能让 Agent 跳过必要审查。本方案将“按场景组合流程”“按失败范围返工”“按真实改动检查审查覆盖”分开处理，避免不断增加固定模板，也避免仅靠 QA 分类判断代码是否已完成审查。

## 四个概念

| 概念 | 职责 | 保存形式 |
|---|---|---|
| Node | 统一编排单位，可直接定义执行内容或引用 Fragment；展开叶子为最小实际执行单位 | 定义在 Fragment 的统一 nodes 中，不单独配置 |
| Fragment | 最小配置文件、复用边界和返工边界；nodes 混合直接节点与 use 引用节点 | `fragments/<name>.yaml` |
| Profile | 工作流模板；声明 Fragment 依赖和有限失败路由，供 LLM 直接采用或参考 | `profiles/<name>.yaml` |
| Plan | 某个需求经校验后固化的执行图、恢复规则和资源快照 | Change 内不可变修订目录 |

Fragment 取消独立 includes。直接节点与 use 引用节点共用 id/requires；引用节点可通过 on_fail.reset 返回同一 Fragment 的上游直接或引用节点，例如本地 implement → 引用 security，失败回到 implement。执行时展开引用内部 Node，不额外执行黑盒任务。

Fragment 不需要 interface 或独立成败文件；引用状态从全部成员汇总：全部完成且 Gate/证据有效才成功，未处理有效 FAIL 才失败，尚未执行不是失败，冲突/损坏结果作为系统错误阻塞。恢复先用内部最近规则，无规则或耗尽后逐层向引用节点传播，最后才考虑 Profile 路由；同一失败只选一个处理者，父重置不清零内层预算。

Profile 不使用通用 Node links，而通过 Fragment 实例的 requires 编排正常流程。其分类恢复来源仍明确到实际 Gate，例如 qa/test；Profile 恢复目标仍是完整 Fragment 实例。

## QA 与交付闭环

```text
实现 Fragment（代码 → 测试 → 必要审查）
    → QA
        ├─ 失败：按预定义分类重跑 FE / BE / 二者，再回到 QA
        └─ 通过：change-assurance 检查全部真实 Diff
                     ├─ 缺失或过期证据：补齐对应流程，再 QA 与保障
                     ├─ 缺失 Fragment：扩张 Plan，再执行所需流程
                     ├─ 未知路径：阻塞，完善规则并修订 Plan
                     └─ 当前证据完整：允许 LoopSpec 内的交付与完成
```

后端实现 Fragment 包含测试、security-review、pr-review；QA 路由到 BE 后会重跑全部成员及下游，不回退业务代码。独立 FE 分支不因 BE 返工自动重置，但其代码若真的变化，旧证据仍会失效。

Gate 采用 begin/record 两步记录：先冻结待审输入，审查结束时确认输入未变，再绑定 PASS。最终保障不能只查看 pass.md 是否存在，而要核对固定基线、当前变更集与具体 Gate 实例的有效证据。保障之后再次改动代码，会重新阻塞交付、完成和归档。

## 核心取舍

- 用 Fragment 完整重跑换取清晰的返工顺序，可能重复一些已完成工作；可以拆分过大的 Fragment 降低成本。
- Profile 保持模板弹性，但项目最低保障约束独立于 Profile；轻量模板不能自动免除真实改动的审查责任。
- 正常依赖是 DAG，返工是单独的有限恢复规则；不引入任意条件执行语言。
- 内部优先便于复用局部恢复，但外层 on_fail 不一定在内部第一次失败时立即触发；系统暴露来源 Gate、所选处理者和传播层级，所有层级耗尽后停止。
- Plan 固化资源、规则和基线，运行时不重新读取模板；来源更新通过新修订生效。
- 普通重组冻结已执行工作；保障触发的增加型扩张显式失效受影响 QA/保障。新修订默认不继承旧代码 Gate PASS，安全但可能增加重审成本。
- 旧 Schema/Change 通过内部适配器继续使用，新模型不强制迁移既有变更。

## 实现顺序与工作量

任务清单共 53 项，目前未开始实现：

1. 第一版本 23 项：统一 Node 模型与兼容 → Fragment 展开/引用基本状态汇总 → Profile/Plan 快照和校验 → CLI 与大型需求、前端小需求、Bugfix 模板。支持直接 Gate 局部恢复，使用人工交付审查，不声称具有第二版本的自动 Diff 保障。
2. 第二版本 24 项：引用 on_fail/嵌套失败传播/分类路由与恢复事务 → Git 清单和 Gate 证据 → 全量 Diff 保障 → Plan 修订与安全扩张。
3. 公共收尾 6 项：英文内置 Skill 源与临时目录投影验证、文档、端到端验证、完整回归和最终安全检查；不修改本地安装目录。

仅支持第一版本的引擎收到含引用 on_fail 或系统保障的第二版本模板时必须明确拒绝，不允许忽略失败规则或假装保障已通过。两版完成后，代码模板默认采用第二版本。

## 安全结论与边界

统一 nodes 与嵌套失败处理的设计级安全复审记录见 security/pass.md；实现阶段仍必须验证重复恢复、父级重置预算绕过、错误结果误路由，以及路径逃逸、资源替换、审批过期、证据重放、并发扫描和事务中断等负向场景。五份规格共 34 条需求、63 个场景，任务仍为 53 项，设计含七段 YAML 示例；这不是代码测试通过的证明。

内容摘要证明审查输入一致，不证明审查质量、测试确实执行或审查者身份。本地文件也不是针对拥有写权限操作者的独立安全边界。LoopSpec 不阻止外部直接 Git 提交；需要独立 CI 或提交工具复核。第二版本按单 Git 工作树设计，不覆盖跨仓库、子模块内部改动或外部提交原子控制；项目需要配置真实路径映射。
